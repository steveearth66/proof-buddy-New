# Developer Notes: Courses & Assignments Module

This document details the underlying technical architecture, relational model mechanics, and quality assurance processes for the Course and Assignment features. It serves as an architectural handoff for future developers maintaining this isolated module.

---

## 1. Architectural & Domain Logic Overview

The courses and assignments system functions as a decoupled module within the application, managing user relationships, provisioning coursework, and orchestrating proof object lifecycles.

### 1.1 Role Enforcements

The backend relies on user properties to isolate capabilities cleanly across API routing:

* `request.user.is_instructor`: Grants permission to instantiate courses, generate token entry arrays, alter deadlines, and read the class-wide evaluation matrix.
* `request.user.is_superuser`: Inherits all instructor permissions globally across all courses, overriding explicit ownership checks.
    > [!NOTE]
    > The superuser accounts do not have a presence in the current state of proofbuddy outside of the django admin page. The permissions in these APIs are for future use and may need to be tightened or loosened as development progresses.
* **Student Profiles (`is_instructor=False`, `is_superuser=False`)**: Restricts access strictly to viewing active enrolled courses, accepting/declining invitations, and creating and working on proofs for assignments.

### 1.2 Isolated Ownership Checks

To prevent multi-tenant cross-contamination, endpoints that mutate data (such as `/assignments/detail/<id>`) check ownership explicitly:

```python
if not request.user.is_superuser and assignment.course.instructor != request.user:
    return Response({"message": "You are not authorized..."}, status=status.HTTP_403_FORBIDDEN)
```

## 2. Database Schema & Table Layouts

### 2.1. `Course` Table

Tracks independent class meta-parameters, security validation hashes, and basic schedules.

| Field Name | Data Type | Null / Blank | Constraints / Options | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `BigAutoField` (Auto) | `False` / `False` | Primary Key | Auto-incremented system record index. |
| `name` | `CharField(255)` | `False` / `False` | | Plaintext course identifier header. |
| `description` | `TextField` | `False` / `True` | `default=""` | Optional contextual overview details. |
| `is_active` | `BooleanField` | `False` / `False` | `default=False` | Guardrail boolean dictating student visibility. |
| `instructor` | `ForeignKey` | `True` / `False` | Restricted to only User accounts where is_instructor is True. | Links to the instructor account that has permission to perform actions on the course. |
| `join_code_hash` | `CharField(128)` | `True` / `True` | | `SHA-256` encoded hash string matching the plain code. |
| `join_code_expires_at` | `DateTimeField` | `True` / `True` | | Explicit timestamp expiration marker (7-day standard limit). |
| `term` | `CharField(20)` | `False` / `True` | The term must be a Season (Spring, Summer, Fall, Winter) followed by a four digit year (ex: Summer 2026). | Format enforcement forcing `[Season] [YYYY]` layout structures. |
| `created_by` | `ForeignKey` | `False` / `False` | Restricted to only User accounts where is_instructor is True. | Tracks row instantiation creator account. |
| `created_at` | `DateTimeField` | `False` / `False` | `auto_now_add=True` | System record creation timestamp. |
| `updated_at` | `DateTimeField` | `False` / `False` | `auto_now=True` | Last modification timestamp. |

* **Implicit Join Table (`Course_students`):** Generated by the `students` `ManyToManyField`.

    | Field Name | Data Type | Description |
    | :--- | :--- | :--- |
    | `id` | `BigAutoField` (Auto) | Auto-incremented system record index. |
    | `course_id` | `Foreign Key` | Id of the course containing the student. |
    | `account_id` | `Foreign Key` | Id of the student User account attached to the course. |

#### Join Token Lifecycle

Join codes balance immediate convenience with database security through automated hashing:

* **Generation:** Utilizes `secrets.choice` to pick 8 secure characters from uppercase alphanumeric characters.
* **Storage:** The plaintext code is never stored in the database. It is stored as a `SHA-256` hex within `course.join_code_hash`.
* **Validation:** When a student enters a code via `/join_course`, the input string is encoded, run through `hashlib.sha256().hexdigest()`, and matched against active courses with unexpired join codes.

| Field Name | Data Type | Null / Blank | Constraints / Options | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `BigAutoField` (Auto) | `False` / `False` | Primary Key | Table entry unique reference integer. |

### 2.4. `StudentProofMapping` Table

Saves background references decoupling sandboxed student workspace modifications from master versions.

| Field Name | Data Type | Null / Blank | Constraints / Options | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `BigAutoField` (Auto) | `False` / `False` | Primary Key | Unique mapping structural reference row index. |
| `assignment` | `ForeignKey` | `False` / `False` | `on_delete=models.CASCADE` | Maps proof to an `Assignment`. |
| `student` | `ForeignKey` | `False` / `False` | Restricted to only User accounts where is_instructor is True. | References user sandbox account workspace owner. |
| `template_proof_id` | `PositiveIntegerField` | `False` / `False` | | Backlink index tracker pointing to master template asset the student's proof was cloned from. |
| `content_type` | `ForeignKey` | `False` / `False` | Value can be: 18 (`inductionproof`) or 20 (`equationalproof`) | System level key defining the type of proof. |
| `object_id` | `PositiveIntegerField` | `False` / `False` | | Unique pointer integer linking the student's proof on the table mapped by the content_type. |
| `completed_at` | `DateTimeField` | `True` / `True` | | Stores the time that the first completed check passes. |

* **Computed Read Properties (Non-Database Fields):**
  * `@property: is_late`: Evaluates boolean state checking if `completed_at` exceeds parent `assignment.due_date`.
  * `@property: started_at`: Pulls row initialization marker `created_at` dynamically from referenced polymorphic `student_proof` instance.

* **Meta Table Properties:**
  * Validation check prevents two rows from existing with the same combination of course and student foreign keys.

## 3. Quality Assurance & Verification Loop

Because the team operates without an automated CI/CD pipeline or tracking tickets, you must manually run local verification before pushing code modifications to the project lead.

### 3.1 Running API Unit Tests

Backend logic is validated through Django's test wrapper. Every critical permissions boundary and serializer constraint is verified automatically.

* **Execution Command:**

  ```bash
  python manage.py test
  ```

* **Scope Coverage:** Validates role authorization failures (e.g., student triggering a course POST), payload validation limits, edge-case date expirations for code strings, and multi-record matching resolution paths.

### 3.2 Manual Frontend UI Test Matrix

Any visual adjustments or interface modifications within the React views must be confirmed using manual verification sweeps. Maintain a clean test db with at least one **Instructor Account** and one **Student Account**, and execute this verification matrix sequence:

| Step | User Account | Dashboard Section | Action Item | Expected UI Outcome |
| :--- | :--- | :--- | :--- | :--- |
| **1** | Instructor | Course Page | Create Course, Toggle Active, Edit Details | Form persists, and properties save correctly. |
| **2** | Instructor | Course Settings | Generate Join Code | Display area shows alphanumeric token and correct date string. |
| **3** | Student | Course Portal | Join via Plain Token | Course appears in user list (must be an `Active` course). |
| **4** | Instructor | Assignment Form | Pick Proofs, Set Expiration, Set Assignment Name | Proof table appends options; assignment created cleanly. |
| **5** | Student | Assignment Deck | Click "Start Assignment" | New proof is created and the user is automatically redirected to the proof. |
| **6** | Student | Sandbox Canvas | Manipulate Lines, Complete Proof | Workspace updates smoothly and flags status as completed. |
| **7** | Instructor | Matrix Dashboard | Click Eye Icon on Assignment | Matrix grid cells color-code dynamically based on student states. |

### 3.3 Defect Management

If any anomalies, unintended database state duplications, or user interface exceptions occur during verification sweeps, document them instantly inside the team's dedicated `#bug-reports` channel  on Discord with:

1. Expected vs. actual behaviors.
2. The endpoint payload data or console stack trace.
3. Precise instructions to reproduce the anomaly locally.
4. If possible, include screenshots for front-end bugs.
