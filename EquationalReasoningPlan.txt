# Equational Reasoning Implementation Plan - Session Summary

## OBJECTIVE
Create a new "Equational Reasoning" proof type by copying/simplifying the working Induction proof system. This will replace the old ERracket mode with a cleaner, modernized version that has the same look & feel as Induction.

## WHY METHOD 2 (New System) vs METHOD 1 (Update Old ERracket)
- **Safety**: Old ERracket works; we don't want to break it
- **Simplicity**: Induction code is fresh, debugged, has all recent fixes (selectedNode persistence, substitution with isMatch, proper error handling)
- **Easier**: Changes needed are mostly REMOVALS of induction-specific complexity
- **Clean Architecture**: New system will match Induction's consistent structure

## ARCHITECTURAL DIFFERENCES: Equational vs Induction

### Backend Differences:
- **Core Object**: `TwoSidedProof` (not `IndProof`)
- **No case parameter**: Everything was `case='base'|'leap'`, now just side parameter
- **Simpler model**: No `induction_variable`, `anchor_value`, `leap_variable`, `inductive_hypothesis_lhs/rhs`
- **Single completion check**: Not base+leap, just one proof

### Frontend Differences (to implement):
- **Title**: "Equational Reasoning" (not "Induction: Racket")
- **No radio buttons**: Remove integers/lists selection
- **Simplified start form**: Keep name/tag, remove ivar/aval/lvar fields
- **No IH fields**: Remove inductive hypothesis inputs
- **No case switching**: Remove "Switch to Leap Case" button and orange "BASE CASE"/"LEAP STEP" text
- **Keep LHS/RHS toggle**: "Switch to Right Hand Side" button stays
- **IH validation**: Rule "apply IH" should error with "IH can only be invoked on Induction proofs"
- **Simpler completion**: Just "Proof complete/incomplete" (not "Base case complete")
- **Single confetti**: Triggers when proof completes (not base+leap)

5. **`check_completion`** (POST `/api/v1/equational/check-completion`)
   - Single check (not base+leap)
   - Returns: `{ isComplete: bool, message: "Proof complete!" }`

6. **`get_proof_lines`** (GET `/api/v1/equational/get-proof-lines`)
   - Returns: `{ LHS: [...], RHS: [...] }`
   - No case filtering

 TECHNICAL NOTES FOR FUTURE DEVELOPERS

### Key Architectural Decisions:

1. **TwoSidedProof vs IndProof**
   - Equational uses expression_tree.ERProofEngine.TwoSidedProof
   - No case parameter anywhere (simplified from Induction's base/leap)
   - LHS and RHS accessed directly: proof_obj.LHS, proof_obj.RHS

2. **State Management**
   - Frontend: racketFields = { LHS: [...], RHS: [...] }
   - Backend: Django cache for session state + conditional DB persistence
   - Cache key: f'equational_proof_obj_{user_id}'

3. **Frontend Component Design**
   - Built from scratch (~400 lines) instead of copying InductionRacket (2400 lines)
   - Cleaner architecture: single proof state (no base/leap complexity)
   - Uses same components: ProofComplete, Substitution (from components/index.js)
   - Service: equationalService.js (6 functions matching backend endpoints)

4. **Backend Conditional Saves**
   - Lines only saved to DB when proof_id exists
   - Enables cache-only testing without database records
   - To enable full persistence: create EquationalProof record on set_current_proof
   - Then proof_id will exist for all subsequent save_proof_line_to_db calls

5. **URL Routing**
   - Backend: /api/v1/equational/* (6 endpoints)
   - Frontend: /#/equational-reasoning (HashRouter requires #)
   - Protected by IsAuthenticated permission class

6. **Testing Strategy**
   - Backend: 11 unit tests in tests.py + integration test in test_integration.py
   - Frontend: Manual testing via TESTING_GUIDE.md
   - All 51 Django tests passing (11 equational + 40 induction)
