Session 2025-12-27 — Debugging and Refactoring Principles (for Future Sessions)
When beginning a new session or debugging issues, follow these core principles:

1. **Incremental Changes with Verification**
   - Make one change at a time and test immediately. Never batch multiple edits without intermediate verification.
   - If you make a change and it breaks something, you know exactly which change caused it.
   - This is exponentially faster than making five changes at once and trying to untangle which one (or which combination) caused the failure.

2. **Verify JSX Structure and Nesting First**
   - When React components break or render incorrectly, the most common culprit is invalid JSX nesting or improper Bootstrap Grid usage.
   - Before diving into state management or logic, visually inspect the component hierarchy: are Row/Col properly nested? Are fragments used correctly? Are conditional renders properly wrapped?
   - Bootstrap Grid rules: Row must contain Col; Col cannot contain Row directly (needs intermediate structure); offset syntax must use object notation in v5.

3. **Console Logging as Surgical Investigation**
   - Add targeted console.log statements at critical decision points: conditional branches, prop values on render, state values before/after updates.
   - Don't add excessive logging that clutters output. Focus on the specific variable/path you're investigating.
   - Once issue is identified, remove or comment out debug logs to keep console clean for future debugging.

4. **Recognize When Reverts Are Better Than Fixes**
   - If fixing one issue creates two more issues, or if cascading failures appear, it's a signal that the approach is fundamentally flawed.
   - Don't be afraid to revert to a known-good state and try a different, more focused approach.
   - Complex refactorings (especially layout changes) often have hidden dependencies. Smaller, targeted changes are safer and easier to debug.

5. **Understand Error Context (User Error vs. System Bug)**
   - Not all errors indicate bugs. Backend validation rejecting mathematically invalid operations (like asserting 0=2) is correct behavior.
   - When a user encounters an error, first determine: Is this the system preventing invalid state? Or is it a genuine failure?
   - Explain to users when errors are actually the system working correctly, not malfunctioning.

6. **Visual Feedback and User Experience**
   - When implementing UI changes, consider visual clarity: color-coding, spacing, borders can dramatically improve usability.
   - Stacked layouts with offset positioning can reduce horizontal crowding while maintaining readability.
   - Alternating colors and gradient transitions help users track relationships between elements.

7. **State and Props Flow**
   - Always trace where state originates and how it flows through components. Don't assume props have the values you expect.
   - Conditional rendering should have clear fallback chains: `proofStarted ? premise : ''` is safer than complex nested ternaries.
   - Separate concerns: display state (what user sees) from data state (what backend knows).

8. **Bootstrap Button Variants and CSS Specificity**
   - NEVER use `variant="secondary"` (or any Bootstrap variant) when you want custom button colors - it applies Bootstrap's default styling which overrides custom CSS classes.
   - Bootstrap variant attributes have higher specificity than custom CSS classes, so even if you add `className="switch-btn"` with a blue gradient, the variant will make it grey.
   - Solution: Either (a) remove the variant attribute entirely and rely only on custom CSS classes, OR (b) use inline styles which have even higher specificity.
   - The `.switch-btn` class applies the blue gradient (`$blue-gradient`), but only works if no variant is specified.
   - When troubleshooting button colors: check for variant attributes first before modifying CSS.

9. **Positioning: Bootstrap Grid vs Explicit Pixels**
   - Bootstrap grid offsets (`offset-md-1`) use percentage-based positioning relative to the container - may not provide enough movement.
   - For precise positioning (especially to avoid overlap with fixed-position elements), use explicit pixel margins (`marginLeft: '190px'`).
   - Always verify code state before applying changes - if replacement tool says "Input and output are identical," the code already has those changes.
   - When visual changes don't appear, check: (1) if code already changed, (2) if approach needs switching (percentage → pixels).

10. **CSS Selector Scoping and DOM Location Dependencies**
   - **Critical principle**: CSS selectors are path-dependent. When styles are nested (e.g., `.container .form .dropdown`), they only apply when the element exists at that exact location in the DOM tree.
   - **Moving elements breaks nested CSS**: If you move a component from inside a form to outside a container, its styles may completely disappear if they were defined with parent selectors.
   - **Solution for portable components**: Define styles at the global level (not nested) so they apply regardless of where the element is placed in the DOM.
   - **Example failure pattern**: `.er-racket-container .er-racket-form .form-top-section .proof-dropdown-btn` only works when dropdown is inside all those parents. Moving dropdown outside the form = no styles.
   - **Example fix**: Extract `.proof-dropdown-btn` to global scope so it works anywhere in the application.
   - **When debugging style loss**: Check if element moved in DOM, then verify CSS selector paths still match the new location.

11. **Flexbox Layout Properties — Root Causes vs Symptoms**
   - **Watch for active forcing properties**: Properties like `justify-content: space-between` actively force elements to spread apart, overriding column sizes and other layout attempts.
   - **Changing column sizes won't fix spreading**: If parent container has `justify-content: space-between`, changing child elements from `md="1"` to `md="auto"` has no effect — the flexbox rule dominates.
   - **Fix the forcing property, not the victims**: Instead of fighting symptoms (adjusting individual element sizes), remove or replace the flexbox property causing the behavior.
   - **Better alternative**: Use `gap: 20px` to create consistent spacing without forcing elements to opposite edges.
   - **Debugging pattern**: When layout changes don't work, check parent container for `justify-content`, `align-items`, `flex-grow` properties that override child settings.
   - **General rule**: Fix root causes (container flexbox rules) before adjusting symptoms (individual element properties).

Session from 2026-01-01: Clear Line Implementation & Array Indexing Alignment

**ROOT CAUSE OF ALL FAILURES:**
The premise was rendered separately (hardcoded) but NOT included in the racketRuleFields array. This created a fundamental indexing mismatch:
- UI Array: index 0 = line 001, index 1 = line 002, etc.
- Database: line 0 = premise, line 1 = line 001, line 2 = line 002, etc.
- Result: racketRuleFields[0] pointed to database line 1, racketRuleFields[1] to line 2, etc.

**WHY STATE UPDATES KEPT FAILING:**
When clearing line 002 (database line_number=2), the code updated racketRuleFields[2], but that was actually database line 3 because of the off-by-one error. State updates targeted wrong indices because array position ≠ database line_number.

**WHY WINDOW.LOCATION.RELOAD() "WORKED":**
Page refresh reloaded everything from database (which had correct data), masking the underlying architectural problem. This was treating the symptom, not the root cause.

**THE ACTUAL FIX:**
Include premise in racketRuleFields array at index 0. Now array index === database line_number:
- racketRuleFields[0] = premise (line 0)
- racketRuleFields[1] = line 001 (line 1)  
- racketRuleFields[2] = line 002 (line 2)

Once indexing aligned, state updates worked correctly without any page refresh.

**CRITICAL LESSON - ARRAY INDEXING ALIGNMENT:**
When you have parallel data structures (UI array, database records), their indexing MUST align. If database uses line_number 0-N, UI array indices must also be 0-N pointing to the same items. Never create separate renderings that cause index mismatches.

**WARNING SIGNS OF INDEX MISALIGNMENT:**
- Calculations like `arrayIndex = databaseLineNumber - 1` or `+ 1`
- Separate rendering for "special" items (premise) that should be in the array
- State updates that only work after page refresh
- Off-by-one errors when accessing array elements by line number

**FIX PATTERN:**
Don't work around index mismatches with arithmetic adjustments. Fix the architecture so indices align naturally, then all code becomes simpler and correct.

**BUG #1: "Invalid Label for Definition" Error Requiring Double-Click to Start Proof**

SYMPTOM:

- Real issue was that FIRST click was using contaminated cached proof from previous session
- check_goal() was conditionally clearing cache only when proof_id was None
- In this case, proof_id was 354 (from old session), so cache wasn't cleared → stale proof object reused → validation error

- Cache key: f"induction_obj_{user.username}"
- Cache persists across server restarts (Redis/Memcached), so old proof_id=354 with UDF '(h x)' contaminated new session
- First Start Proof attempt: check_goal loads cached IndProof with wrong UDF → 'f' definition corrupted → validation fails
- Second Start Proof attempt: start_induction_proof clears cache → fresh validation → works

```python
# BEFORE (lines 95-101):
ind, proof_id = get_or_set_induction_obj(user)

    cache.delete(f"induction_obj_{user.username}")

```

**BUG #2: Generic Variable Created with enabled=true but Showing as Disabled in UI**

SYMPTOM:
- When starting induction proof, backend creates generic 'k' 
- Frontend saves it to sessionStorage with enabled=true
- Console logs show generic saved correctly with enabled=true
- Definitions panel shows "Enable" button (meaning enabled=false) instead of "Disable"
- SessionStorage inspection shows "enabled":false despite console showing it was saved as true

INITIAL HYPOTHESIS (WRONG):
- Believed CustomEvent 'genericsUpdated' system was broken
- Event was being dispatched but never received by Definitions component
- Thought it was React lifecycle timing issue (component mounting/unmounting removing event listener before event fired)

WHY THIS WAS WRONG:
- Event system being broken wasn't causing the bug - just a red herring
- UI was correctly updating via useEffect sync that reads from sessionStorage (Definitions.jsx lines 353-380)
- Buttons initially showed "Disable" correctly, then CHANGED BACK to "Enable"
- This wasn't an event timing issue - data was being OVERWRITTEN after initial save

CRITICAL DEBUGGING CLUE:
- User's sessionStorage screenshot showed "enabled":false even though console.log showed it was initially saved as enabled=true
- This meant something was overwriting sessionStorage AFTER the initial save
- Searched for all sessionStorage.setItem('generics') calls in codebase

ROOT CAUSE:
Definitions.jsx has a useEffect (lines 590-620) that calls erService.getUserGenerics() to fetch all generics from backend database. The merge logic was:

```javascript
// OLD BROKEN MERGE:
const merged = [...userGenerics];  // Start with backend data
storedGenerics.forEach(stored => {
  const existsInBackend = userGenerics.find(ug => ug.label === stored.label);
  if (!existsInBackend) {
    merged.push(stored);  // Only add if not in backend
  }
});
```

EXECUTION SEQUENCE:
1. InductionRacket saves k with enabled=true → sessionStorage ✓
2. Definitions mounts, reads sessionStorage (k has enabled=true) ✓
3. Buttons render "Disable" correctly ✓
4. getUserGenerics() API call completes → backend returns k WITHOUT enabled field (backend model doesn't have this UI-only field)
5. Merge logic blindly accepts backend data → overwrites sessionStorage with backend version (no enabled field) ❌
6. Component re-renders, enabled=undefined → defaults to false ❌
7. Buttons now show "Enable" (wrong)

THE FIX:
Modified Definitions.jsx lines 590-620 to preserve enabled state from sessionStorage during merge:

```javascript
// NEW WORKING MERGE:
const merged = userGenerics.map(backendGen => {
  const storedGen = storedGenerics.find(sg => sg.label === backendGen.label || sg.name === backendGen.name);
  if (storedGen) {
    // Preserve enabled state from sessionStorage
    return { ...backendGen, enabled: storedGen.enabled ?? backendGen.enabled };
  }
  return backendGen;
});

// Add any sessionStorage generics that don't exist in backend yet
storedGenerics.forEach(stored => {
  const existsInBackend = merged.find(ug => ug.label === stored.label || ug.name === stored.name);
  if (!existsInBackend) {
    merged.push(stored);
  }
});
```

Also normalized field names (added both 'label' and 'name' fields) in InductionRacket.js so merge matching works correctly, since backend uses 'name' but sessionStorage uses 'label'.

KEY LESSONS FOR FUTURE DEBUGGING:

1. **Don't chase red herrings** - Event system not working was a distraction; the UI was updating fine via other means
2. **Look for overwrites** - When saved data doesn't match retrieved data, search for ALL places that write to that storage key
3. **Backend models ≠ Frontend state** - Backend doesn't include UI-only state (like 'enabled'). Always preserve local state during merges with backend data
4. **SessionStorage inspection is critical** - Checking Application tab in DevTools reveals discrepancies between console.log and actual stored values
5. **Field name normalization matters** - Mismatched field names ('label' vs 'name') can break merge logic silently
6. **Async data fetches can overwrite local state** - When component mounts, useEffect hooks fire API calls that can clobber freshly-saved data

DIAGNOSTIC PATTERN FOR SIMILAR BUGS:
- User reports "I saved X but UI shows Y"
- Console.log shows X saved correctly
- Check sessionStorage/localStorage in Application tab - if it shows Y, something is overwriting it
- Search codebase for ALL writes to that storage key (grep for setItem)
- Look for async API calls (useEffect, .then()) that merge/overwrite data
- Verify merge logic preserves frontend-only fields when combining with backend data

ENVIRONMENT NOTE: Running Django Tests on Windows

To run `py manage.py test` on Windows, always set the terminal encoding first:

    $env:PYTHONIOENCODING="utf-8"; py manage.py test

WHY THIS IS NEEDED:
- Several test files use Unicode characters in print() statements (e.g., → \u2192, ✓ \u2713)
- Windows PowerShell terminals default to cp1252 encoding, which cannot encode these characters
- Without the env var, Python raises UnicodeEncodeError inside the test print() calls, causing those tests to be reported as ERROR instead of PASS/FAIL
- This is not a code bug — it is purely a terminal encoding issue
- Setting PYTHONIOENCODING="utf-8" tells Python's stdout to use UTF-8, allowing the Unicode characters to print correctly
- Do NOT "fix" this by replacing Unicode characters in test files — that changes source code unnecessarily and the env var is the correct solution
