EQUATIONAL REASONING - PROJECT STATUS (January 2, 2026)

We have successfully created a new "Equational Reasoning" proof type to replace the old ERracket system. The backend is 100% complete with a Django REST API (equational_reasoning_api app) featuring 6 endpoints: set_current_proof, apply_rule, substitution, delete_line, check_completion, and get_proof_lines. All backend tests are passing (11 unit tests + integration tests). The backend uses the TwoSidedProof engine (not IndProof) and stores proofs in EquationalProof/EquationalProofLine models with conditional database persistence.

The frontend EquationalReasoning component has been rebuilt from scratch with a full 3-pane layout matching InductionRacket's structure. The Header pane contains persistent proof parameters (Name, Tag, LHS Goal, RHS Goal) plus read-only Current LHS/RHS displays. The Middle pane shows proof lines with ClickableRowNumber components for binding, PersistentPad rendering for each line with interactive highlighting, and a blank line at the end indicating where the next proof line will appear. The Footer pane has a "Num" input field with a "FILL VALUES" button (when unbound), an editable PersistentPad (when bound to a line), and action buttons (CLEAR LINE, GENERATE & CHECK, SUBSTITUTION). The component routes to /#/equational-reasoning and is integrated into the homepage dropdown menu.

Several bugs have been fixed including HashRouter URL navigation, substitution modal crashes (prop name mismatch), missing line selection tracking, line overwriting instead of insertion, and jsonTree property name mismatches (backend sends lhsJsonTree/rhsJsonTree, frontend now correctly reads these). PersistentPad integration is working with refs (lhsPadRefs, rhsPadRefs, footerPadRef), node selection tracking, and jsonTree data flowing from backend to frontend.

However, the layout still needs significant adjustments to match the exact InductionRacket UI/UX. The component is functional but requires refinement in styling, spacing, button placement, footer pane behavior, and overall user interaction flow. Testing is needed for: (1) Starting a proof and verifying premise lines display correctly, (2) Binding to line 000 and using arrow keys to select nodes for highlighting, (3) Generating line 001 with "eval +" rule, (4) Testing substitution with "eval if" to verify the bug fix, (5) LHS/RHS toggle functionality, (6) Clear line feature, (7) Proof completion checking, (8) Error handling and edge cases. The FILL VALUES button behavior, footer pane binding/unbinding flow, and proof line highlighting during editing all need to be tested and potentially adjusted to match the InductionRacket experience exactly.
